斗六分院與成大醫院 Phase-1 上線

第 300 天前，把改寫後的 C# HIS 在斗六分院與成大醫院正式上線，取代 VB.Net 版——這是 50% 付款的驗收條件。HIS 不能中斷（貳-三-4），所以不是「切換」而是「兩套並存、逐步搬移、隨時可退」。我們的核心主張：資料庫不動、只換應用層，切換單位是工作站／科室，回退動作是改一張設定表。做不到這點，任何 cutover 策略都是賭博。

規格原文依據

貳-一-(一)-5：「以上開發範圍於整合測試完成後，廠商應安排先行於斗六分院與成大醫院上線使用。」

貳-三-2：「…提交『導入步驟工作書』、『測試步驟工作書』、『上線前檢核清單』、『緊急復原工作書』供本院確認。」

貳-三-4：「HIS 服務不能中斷，需求調整亦需持續上版，得標廠商必須提供規劃以確保新舊版本功能一致。」

貳-三-5：「程式調整完成後，需模擬新版本運作環境進行完整測試，並與本院使用者及資訊人員共同測試。」

伍-三-8：「上線前應清除正式環境之測試資料與帳號及管理資料與帳號。」

三階段表：第一階段交付「程式設計書、測試報告書、原始程式碼（電子檔）」，決標次日起 300 天內，付款 50%。

規格沒說：上線順序（斗六先或成醫先）、是否允許並存期、client 部署方式、測試環境誰出、Phase-1 上線時成醫現有的院內介接（LIS、PACS、MIS…）是否要全數驗證。最後一項是最大的隱藏範圍——X01 寫的是老醫的介接測試，但成醫切到 C# 那天，成醫現有的每一條介接都得照常運作。

我們預期的系統樣貌

元件與資料流

  • cutover 策略比較：(a) 大爆炸週末：一次全換，回退也是一次全退；對 3,900 支程式與數千台 PC 太危險，否決。(b) 平行運行：使用者兩套都打，資料會重複，臨床不可能接受，否決。(c) 先導科室：好，但單一科室不能驗證跨系統流程。(d) 依模組分波：門診→急診→住院，每波內部流程完整，波與波之間靠同一顆 DB 互通。我們採 (c)+(d)：斗六全院當先導，成醫依模組分波。
  • 資料相容性：Phase-1 期間 C# 新增的表（T02 的設定表）與欄位只允許「additive」，禁止改型別、刪欄、改 stored procedure 語意；C# 寫進去的資料 VB 必須讀得懂（T05 的 golden output 比對即是驗證）。這是回退可行的前提。
  • 回退計畫（緊急復原工作書）：三個層級。L1 單工作站回退：改設定表、重啟 launcher，5 分鐘。L2 整波回退：設定表批次更新 + 通知該科，30 分鐘內。L3 全院回退：所有工作站指回 VB、C# 後端停止，1 小時內；前提是 VB 後端在 hypercare 結束前不下線。定義「不可回退點」：VB 後端下線後，或任何非 additive 的 DB 變更執行後。
  • Client 佈署：院方現行更新機制規格未載明，需確認（ClickOnce？自製 launcher？群組原則？）。無論何者，.NET runtime、C# client 程式與 WCF 端點設定需在切換前一週預佈到所有 PC（「預佈、後啟用」），切換當天只改設定表。需要院方 PC 清單（工作站代碼、科室、OS 版本、外接設備）。
  • 測試環境（Wave 0）：DB 複本（近期正式資料，去識別化程度需與院方談）、C# 應用伺服器、VB 後端一份（做並存與 golden output）、20 台代表性 client（含讀卡機、處方箋印表機、藥袋標籤機、條碼機）、健保測試卡與測試 VPN、現有院內介接對象的測試端（LIS、PACS、MIS 至少要有）。院方出硬體（貳-二-(三)），我們出建置與腳本。
  • 整合測試與 UAT：依貳-三-5 需與使用者及資訊人員共同測試。以子系統為單位（共 67 個）寫測試腳本，每個子系統至少一位院方 key user 簽認；門診、批價、藥局、住院醫囑、健保申報五個高風險模組做端到端劇本測試。
  • 上線前檢核清單：T05 登錄簿全數已回歸、凍結窗已生效、伍-三-8 測試帳號與資料清除、弱掃結果（M03）、回退演練已做過一次、war room 名單與叫修專線。

工作量怎麼估的

整合測試腳本撰寫與執行（67 子系統 × 兩院區參數，約 12 人月）；UAT 協調與缺陷追蹤（6 人月）；client 打包、預佈工具與 PC 盤點（4 人月）；cutover 計畫、四份工作書中與上線相關的三份、回退演練（6 人月）；五波切換每波 2–3 人現場守 1–2 週（8 人月）；hypercare 兩院各 4 週（4 人月）。合計約 40 人月。若成醫現有院內介接必須在 Phase-1 逐條驗證（很可能），要再加 6–10 人月，這部分應與 X01 合併估。

需要的領域知識與難點

  • 醫院作業節奏：門診切換選週末、急診沒有低峰只有相對低峰（凌晨 2–5 點）、住院切換要避開月底健保申報與月初結算；月底／月初批次（262 支）跑的時候不能切。
  • 健保 IC 卡與申報連續性：切換當天讀卡、寫卡、就醫序號、每日上傳不能斷；VB 與 C# 若同時對同一台讀卡機／同一張卡操作要有互斥。
  • 批價與藥局的零容錯：批價金額、藥袋內容一旦不一致會直接影響病人與健保核刪，這兩個模組的 golden output 比對必須 100% 一致才能切。
  • 斗六與成醫的院區差異：斗六先導的價值在於驗證 T02 參數化——同一份碼、不同院區設定。若斗六其實有獨立分支程式（需確認），先導的代表性會打折。
  • 成醫現有介接：LIS、PACS、MIS、電子病歷等現有介接在 C# 版上的行為必須與 VB 版一致，這需要各介接原廠配合測試，而規格只承諾提供「標準介接說明」。

依賴關係

前置任務

  • T01 — 上線的標的物本身；T01 未完成的子系統無法進入整合測試。上線波次順序（門診→急診→住院）應反過來約束 T01 的改寫順序。
  • T02 — 斗六與成醫用同一份碼靠院區參數區分；「工作站→版本」切換表也建在 T02 擴充的 PCS_Ip_Config 上。
  • T03 — 效能不得低於 VB 版；上線前檢核要有壓測結果（門診尖峰掛號、批價）。
  • T04 — SQL 移後端與 HTTPS 改變部署拓樸（憑證、防火牆、WCF 端點），必須在測試環境先驗證。
  • T05 — 凍結窗與登錄簿「全數已回歸」是上線門檻；並存期間的資料相容性靠 golden output 比對證明。
  • M01 — 導入步驟工作書、測試步驟工作書、上線前檢核清單、緊急復原工作書四份都在上線前要院方確認。

依賴本任務的任務

  • T16 — 成醫與斗六必須先站在 C# 版上，老醫版本才能「回饋」；Phase-1 的並存架構與 launcher 切換表在 Phase-3 直接重用。
  • T08 — 數據整合中台的 CDC／Replication 來源是 Phase-1 上線後的正式 DB，其 schema 與寫入行為由 C# 版定義。
  • 驗收付款 50% 直接掛在本任務。

主要阻礙與風險

  • T01 進度就是上線進度 — 300 天要改寫 3,900 支程式再整合測試，若 T01 在第 220 天前未完成 90% 以上，整合測試與五波切換擠不進剩下時間。這是全專案最大的排程風險。
  • 並存架構可能不被允許 — 若院方基於維運考量要求一次切換，回退將變成全院回退，風險級別完全不同。
  • 成醫現有介接的隱藏範圍 — 規格把介接測試放在 Phase-2（老醫），但成醫 Phase-1 切換就會碰到；原廠配合度與費用都未定。
  • Client 佈署規模 — 數千台 PC、OS 版本混雜、.NET runtime 差異，預佈失敗的 PC 在切換日會直接變成臨床事件。
  • 測試環境延遲 — 院方出硬體，時程不在我們手上；DB 複本的個資去識別化也需要院方決策。
  • 健保申報週期 — 每月 1–20 日申報期間住院與批價不宜切換，實際可用切換窗比日曆少一半。
