T08

數據整合中台

Phase 2 的技術基石。規格要求用 CDC／MQ／Replication 把各院區 HIS 的掛號、床位、排程、手術、檢驗、供膳等資料即時供應到一個讀取層，讓跨院查詢（T09–T14）不直接打核心 HIS 資料庫，達到讀寫分離；同時要有清檔機制，並銜接成大的住院健檢歷史資料，未來擴充 Dashboard／Analytics。規格只給了三個技術名詞，沒有給資料庫引擎、資料量、拓樸，所有架構決策都要先問。

規格原文依據

貳-一-(二)-7 數據整合中台：「配合跨院區作業查詢需求，透過資料即時供應機制（例如 CDC、MQ 或 Replication）提升資料即時性與效能，保護核心 HIS 資料庫並達到讀寫分離，後續可支援 Dashboard、Analytics Application 等加值應用。」

  • 「跨院資源共享：掛號資訊、床位資訊、檢查科室儀器排程、開刀房手術排程、檢驗抽血、營養供膳等。」
  • 「需有清檔規劃機制。」
  • 「能銜接原本在成大醫院的住院健檢資料（帶出受檢者歷年受檢資料與報告為住院健檢系統原有核心功能）。」

貳-二-(三)：「本院會提供本案所需的軟硬體環境及周邊平台相關資料予得標廠商。」貳-一-(五)-1：「資訊室 DC 組統籌伺服器安裝與建置，上線前另建置一組對應環境供測試。」

規格未載明：資料庫引擎與版本、各院區是否各自一套 DB、資料量、跨院網路、即時性目標（秒級或分鐘級）、中台由誰維運。全部需確認。

我們預期的系統樣貌

原則：中台是唯讀的。跨院「查詢」走中台；跨院「辦理」（掛號、預約、轉檢申請）不經中台寫入，而是呼叫擁有該資料的院區 HIS 後端服務（C#／WCF over HTTPS，T04）寫入該院核心 DB，再由 CDC 把結果流回中台。這就是讀寫分離的具體意義，也是避免中台變成第二個真相來源的關鍵。

元件與資料流

  • 擷取層。假設核心 DB 是 SQL Server（VB.Net + WCF 的 2011 年系統極可能，但規格未載明），首選 SQL Server CDC（log-based，對 OLTP 影響小，不用改任何一支 HIS 程式）。若版本／版次不支援 CDC（2016 SP1 前的 Standard 不支援），退而用 Transactional Replication 直接複寫到讀取庫，犧牲轉換彈性。若是 Oracle 則改用 LogMiner／GoldenGate 類工具，成本大不同，這就是為什麼引擎版本是 P0。
  • 訊息層。MQ 的用途是解耦與緩衝：院區間網路斷線時訊息留在 queue，恢復後補齊；也讓多個消費者（ODS、未來 Analytics）訂閱同一份異動。不要為了規格上寫的三個詞全部都做——CDC + MQ 一組、或 Replication 單獨一組，二選一。
  • ODS 讀取庫。統一 schema，主鍵一律含院區代碼（沿用 T02 的院區參數）。三院的表結構在 Phase 1 後理論上一致，但 Phase 2 期間總院持續增修（T05）會讓 schema 漂移，中台 loader 要能容忍多欄位。
  • 查詢 API。C# 服務，只讀，有分頁與快取，所有查詢寫存取紀錄（伍-三-6、伍-一-8 保存 5 年）。跨院看病人資料屬跨機構個資利用，API 要帶目的與操作者。
  • 清檔機制。依資料域訂保存年限：掛號／床位／排程異動明細短期（例如 2 年），住院健檢歷史依「歷年受檢資料」需求永久保留（或依病歷保存年限）。清檔是排程作業加歸檔，不是單純 delete。
  • 住院健檢歷史。「帶出受檢者歷年受檢資料與報告」代表要把成大現有住院健檢系統的資料（含報告檔，可能是 PDF／影像）搬到或連到中台，讓老醫端可讀。報告檔在哪、多大、格式為何，規格未載明。
  • 即時性目標（我方提案，待院方確認）。床位／掛號 ≤ 10 秒；檢查與手術排程 ≤ 60 秒；供膳統計每日批次即可；健檢歷史一次轉置加每日增量。

工作量怎麼估的

平台骨幹（CDC 設定、MQ、loader、監控、重播、環境）約 8 人月；六個共享資料域各約 2 人月（schema 對映、資料清洗、查詢 API、測試）合計 12 人月；清檔機制與住院健檢歷史轉置約 4 人月。共 24 人月，前提是 DB 是 SQL Server 且 DC 組能在 Phase 2 前 2 個月給環境。若引擎不是 SQL Server 或三院 DB 拓樸複雜（例如斗六與總院共用一套 DB 但老醫獨立），加 30%。

需要的領域知識與難點

  • HIS 資料模型。掛號、床位、排程、手術、檢驗、供膳六個資料域橫跨門診／住院約 20 個子系統的表；要知道哪些表是主檔、哪些是異動、狀態欄位怎麼解讀（例如床位「佔床／待清／保留」在總院是怎麼表示的）。沒有資料字典就是逆向工程。
  • CDC／Replication 的運維知識。log 保留、cleanup job、schema change 對 capture instance 的影響、initial snapshot 對 OLTP 的鎖定影響。HIS 不能中斷（貳-三-4），初始快照必須在離峰做。
  • 個資與跨機構資料利用。若老醫是獨立醫事機構，跨院查病人資料涉及個資法目的外利用與醫療法病歷調閱規範；中台的存取紀錄與授權設計要對得上 M03 的防護需求等級評估。
  • 最終一致性的產品設計。使用者在跨院畫面看到的床位是「幾秒前」的狀態，辦理時要回到擁有院 HIS 再檢核一次。這個「先查後辦、辦時再驗」的模式要讓 T09–T12 的設計者理解，否則會出現在中台上看到空床、實際去辦已被佔的情況。

依賴關係

前置任務

  • T02 — 院區代碼與院區設定表是中台所有資料的分割鍵；T02 定義的 PUB_Config／新設定表也是中台判斷「哪個院區擁有哪筆資料」的依據。
  • T07 — 共享資料域的細部範圍（例如檢查排程要到儀器層級還是科室層級）由基準文件決定；平台骨幹可以先做，資料域範圍要等 T07。
  • （環境依賴，非任務）DC 組伺服器與測試環境：規格把它放在 T15（貳-一-(五)-1），但中台在 Phase 2 就需要，必須提前向 DC 組要。

依賴本任務的任務

  • T09 掛號、T10 床位、T11 手術排程、T12 檢查排程、T13 供膳統計、T14 轉檢代檢 — 全部的跨院「查詢」面都從中台讀。
  • T15 — 老醫上線環境要含中台的正式與測試環境；住院健檢歷史轉置是資料轉置的一部分。
  • M03 — 中台是新增的資通系統，需要納入防護需求等級評估與弱掃。

硬體／外部設備介接

無。中台是純軟體平台。但它需要新的基礎設施：每院一組 capture 節點、MQ 叢集、ODS 資料庫伺服器、查詢 API 伺服器，正式與測試各一套。規格明訂伺服器由 DC 組統籌（貳-一-(五)-1），本案不採購硬體，但我們要提出規格需求（CPU／RAM／磁碟／網路）並在 Phase 2 初就要到。

主要阻礙與風險

  • 來源 DB 未知 — 引擎、版本、拓樸皆規格未載明。這是投標估價最大的不確定項，也是 Phase 2 第一週就要解掉的事。
  • 環境給得太晚 — 規格把伺服器建置放在 Phase 3 T15；中台在 Phase 2 前段就要有環境。若 DC 組依規格時程給，T09–T14 全部延後。
  • schema 漂移 — Phase 2 期間總院 HIS 持續增修（T05），共享資料域的表會改；CDC capture instance 遇到 schema change 需要重建。要在 T05 的合併流程加一道「中台影響評估」。
  • 初始快照對 OLTP 的衝擊 — HIS 不能中斷。大表初始同步要在離峰、分批，且要院方核准時段。
  • 中台被當成寫入路徑 — 若 T09–T12 的設計者圖方便直接寫中台，讀寫分離就破功且會出現雙重真相。必須在架構規範中明文禁止並在 code review 把關。
  • 個資與跨機構利用 — 老醫若為獨立機構，中台等於跨機構病人資料流通，需法遵設計（授權、目的、紀錄）；M03 的防護等級若被評為高，控制措施成本上升。
  • 「Dashboard／Analytics 擴充」的範圍解讀 — 規格說「後續可支援」，我們解讀為本案只留擴充點不做應用；需在 T07 基準文件白紙黑字寫成 Out-of-scope。
