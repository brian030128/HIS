H07

自動繳費機介接（開發）

讓病人在老人醫院的自助繳費機查詢待繳費用、以現金／信用卡／電子票證／行動支付付款、列印醫療費用收據與領藥單，並讓收款正確回到 HIS 批價、當日與出納對得上帳。這是四個設備介接中最難的一個：碰錢、碰法定收據、碰多家支付機構，任何一筆對不上都是出納的事故。繳費機本身是廠商設備，HIS 這側要提供一組嚴謹的批價／收款／退費 API 與對帳機制。規格未載明廠牌、支付通路與收據型式。

我們預期的系統樣貌

元件與資料流

  • ① 查詢待繳：以健保卡（讀卡機取身分）、病歷號＋生日、或繳費單條碼識別病人，回傳未繳的門診／急診批價單，明細要能分列健保部分負擔（診察、藥品、檢查、藥事服務）與自費。查詢同時要鎖定該批價單，避免櫃台與繳費機同時收款；鎖定要有逾時釋放。
  • ② 收款：全部在 kiosk 端由廠商驅動周邊；HIS 不碰端末機。但 HIS 要知道每種支付別的欄位（信用卡授權碼、末四碼、端末機批次號；電子票證交易序號與卡號末碼；行動支付的交易 ID），對帳時要用。
  • ③ 確認收款：kiosk 拿到支付成功後呼叫 HIS 銷帳，HIS 發收據號、記收款方式與繳費機站別，回傳收據與領藥單的列印內容（或版面資料）。這一步必須冪等：kiosk 重送同一筆不能重複銷帳；HIS 逾時未回而 kiosk 已扣款，要有補償查詢。
  • ④ 列印：醫療費用收據是法定格式（醫院統編、收據編號、項目分列、健保／自費），版面與編號規則由院方會計室定，HIS 給資料，kiosk 印。醫療服務依營業稅法第 8 條免稅，醫院開的是醫療費用收據而非統一發票；只有非醫療自費商品才可能涉及電子發票，是否有此情境要問，若有就要接財政部電子發票平台或加值中心，工作量會明顯增加。
  • ⑤ 作廢／退費：當日同交易可由 kiosk 作廢並原路退回（信用卡取消授權、電子票證退值、現金退鈔），跨日或部分退費一律到櫃台；HIS 要提供作廢 API 並鎖住已產生的領藥單／檢查單。
  • ⑥ 日結對帳：三份資料要對得上：HIS 收款紀錄（依站別、支付別）、kiosk 交易檔（含現金抽屜計數）、各支付機構結帳單（端末機 settlement、票證日結、行動支付對帳檔）。HIS 提供對帳報表給出納組，差異要能標示到單筆。
  • 住院：住院中途繳費（預繳）與出院結帳是否上繳費機，成大現況未知；若要，出院管理系統與住院健保都要開 API。

工作量怎麼估的

約 8 人月：與總院現行介接和收據規則對照 0.5、待繳查詢／鎖定／銷帳／作廢 API 含冪等與補償 2、收據與領藥單資料組裝（法定格式、三院不同版面參數化）1、對帳報表與出納流程 1、門診批價與住院端配合修改 1、kiosk 模擬器（可跑全部交易情境與故障注入）0.5、廠商聯測、各支付機構測試、資安檢測（M03，碰金流會被重點查）、上線現場 2。若含住院結帳加 1.5；若涉及電子發票加 1.5～2；若廠商堅持 DB 直連而非 API，反而要多做一層相容 View 與觸發器，加 1。

需要的領域知識與難點

  • 健保部分負擔與批價規則：門診基本部分負擔、藥品與檢查部分負擔級距、慢箋免部分負擔、重大傷病／低收入／榮民免負擔、急診依檢傷級數收費（與 H01 相關）、掛號費各院不同、自費項目定價。繳費機只顯示 HIS 算好的數字，但顯示分類錯了病人就投訴，而且健保申報與收據要一致。
  • 醫療費用收據法定要件與編號：收據是報稅與保險理賠憑證，補印、作廢、重開都有規則；收據號一旦跳號出納要解釋。三院收據版面與編號規則可能不同（T02）。
  • 金流與對帳：每種支付通路的授權、結帳、退款時序不同（信用卡當日取消 vs 隔日退刷；電子票證退值限制；行動支付 T+1 對帳檔）。出納組的日結流程是我們要配合的，不是我們定的。
  • 冪等與故障處理：扣款成功但 HIS 未銷帳、HIS 銷帳但收據未印出、找零卡鈔中途中斷──每種都要有明確的補償路徑與人工處理畫面，這是繳費機上線後最多客訴的來源。
  • 資安與個資：API 對 kiosk 網段開放，必須 HTTPS（T04）、雙向驗證或 API key、卡號不落地（PCI DSS 是端末機廠商與收單行的事，但 HIS 不能存全卡號）、交易日誌加密保存（伍-三-7）。M03 滲透測試會打這組 API。
  • 高齡使用者：老醫病人操作 kiosk 有困難的比例高，院方可能要求志工協助模式、超時自動取消、放大字體與語音；這些在 kiosk 端，但「超時自動取消」要 HIS 鎖定釋放配合。

主要阻礙與風險

  • 多方外部相依 — 繳費機廠商、收單銀行、票證公司、行動支付機構各自有測試環境與排程，任何一方延遲整條聯測就卡住；這些合約都是院方簽的，我們無法直接推。
  • 錢對不上 — 冪等、補償、作廢流程若有一個漏洞，就是出納每天要人工調帳；上線初期一定會發生，要預先設計人工處理畫面與 SOP。
  • 電子發票範圍不明 — 若院方臨時要求開發票，架構與時程都要重排。
  • 廠商要 DB 直連 — 舊繳費機介接常是廠商直接讀寫 HIS 表；T04 要求 SQL 移後端，廠商端改成呼叫 API 需要廠商配合與費用，院方採購合約若沒寫進去就會僵住。
  • 資安檢測 — 金流 API 是滲透測試重點；HTTPS、憑證、卡號不落地、日誌加密都要在設計期做，不能事後補。
  • 與 T01 批價改寫耦合 — 門診批價是門診 27 子系統中規則最重的，改寫延後本任務就沒有掛載點。

待確認問題

  1. 老醫繳費機支援哪些支付通路？特約銀行與票證機構是誰？合約由誰簽、何時生效？
  2. 收據是否全為醫療費用收據？有無任何需開統一發票／電子發票的項目？
  3. 收據號由 HIS 發還是 kiosk 發？補印與作廢規則？三院版面是否相同？
  4. 是否支援住院中途繳費與出院結帳？部分繳費？
  5. 當日作廢與退費的規則：哪些支付別可原路退回？跨日一律櫃台？
  6. 總院現行介接是 API、WCF 還是 DB 直連？廠商是否願意改成呼叫新 API？費用由誰出？

  8. 出納日結是以 HIS 報表為準還是 kiosk 報表為準？差異處理由誰負責？
