T01

VB.Net→C# 全面改寫

把成大醫院／斗六分院現行 VB.Net HIS（門診、急診、住院、醫療共用四大系統；線上約 3,647 支、批次約 262 支、另有未盤點的本機獨立程式）全部改寫為 C#，且功能與現行版本一致。這是全案最大的單一工作項目，Phase 1 付款 50% 的主體，也是 T02～T06 與整個老人醫院導入的地基：沒有它，其他任務都只是紙上設計。

規格原文依據

貳-一-(一)-1：「程式原始碼由 VB.Net 改寫為 C#，包含門診、住院、急診系統的前後端程式及批次程式。HIS 共四大系統分類，線上作業約 3,647 支、批次作業約 262 支，另有隨業務需要不定期在本機端執行的獨立程式（之後盤點）。」子系統數：醫療共用 8、門診 27、急診 7、住院 25（附錄）。

貳-二-(一)：「開發工具：Microsoft Visual Studio 2022；程式語言：C#。」

壹-四-1：「以現行在成大醫院及斗六分院運行的 HIS 為基礎，進行系統整合面的分析與開發……以達到一致性、擴充性及易於維護的目標。」

貳-三-4：「HIS 服務不能中斷，需求調整亦需持續上版，得標廠商必須提供規劃以確保新舊版本功能一致。」

階段一交付：程式設計書、測試報告書、原始程式碼（電子檔）。

規格只規定語言（C#）與 IDE（VS 2022）。UI 技術（WinForms／WPF／Web）、.NET 版本（Framework 4.8 或 .NET 8）、資料庫（推測為 SQL Server，因 PCS_Ip_Config／PUB_Config 為資料表命名，但規格未載明）、主機平台（IIS／Windows Service）都規格未載明，需確認。

我們預期的系統樣貌

現行系統啟用於民國 100 年（壹-二），以 VB.Net + WCF 為世代特徵，最合理的推測是：WinForms 胖客戶端 → WCF 服務（IIS）→ SQL Server，批次以 Windows 排程執行 exe。我們的目標架構刻意不改變拓樸，只換語言與整理分層——因為規格寫的是「改寫」不是「重新設計」，且 300 天內要在兩院上線，任何 UI 典範轉移（改 Web、改 WPF）都會把使用者重新訓練與流程風險加進來，付不起。

元件與資料流

  • HIS.Client（C# WinForms）：每支 VB Form 對應一支 C# Form。表單只做 UI 與呼叫服務；所有 SQL、院區判斷、檢核邏輯搬出去（分別是 T04、T02、T03 的產出）。
  • HIS.Shared Kernel：Context（登入者、院區、站台、IP）、共用 DTO、錯誤處理、Logging、IC 卡／印表／條碼 wrapper。這一層要在轉換量產前先做好，否則 3,900 支程式各自長出一套。
  • HIS.Services（WCF）：維持 WCF（規格 貳-一-(一)-4 明示 WCF 要支援 HTTP/HTTPS，等於指定 WCF 留下）。依附錄的 67 個子系統切 ServiceContract；不做微服務。
  • HIS.Batch：262 支批次收斂到一個 host（一個 exe，多個 job class），排程時間與參數沿用；日誌與失敗告警集中。
  • 資料庫：Phase 1 原則上不動 schema（只加 T02 的設定表）。三院是否共用一個 DB 或各自一個 DB，會決定 Context 的設計，規格未載明。
  • .NET 版本決策（建議）：Phase 1 用 .NET Framework 4.8 + C#。理由：(1) WCF 服務端原生支援，CoreWCF 在 .NET 8 上可行但多一層風險；(2) VB 與 C# 組件可在同一個 solution 混編、同一 CLR 互相參照，這是能做 strangler 逐模組替換的前提；(3) 院內 Client 端 OS 與 .NET runtime 現況未知。若院方要求 .NET 8，估算加 15–20%。需院方拍板。

遷移策略（這是本任務成敗的核心）

  • 工具轉換為主、人工修整為輔，不逐支手寫。3,900 支手寫在 300 天內不可能。用 Roslyn 型 VB→C# 轉換器（ICSharpCode CodeConverter 這類，或自建）做第一輪，配上我們自己寫的 Roslyn analyzer／code-fix 批次處理已知模式：內嵌 SQL 字串（→T04 標記）、院區 if-else（→T02 標記）、On Error Resume Next、late binding（Option Strict Off）、My.*、Form 預設實例（Form1.Show()）、IIf 非短路、整數除法 \、Option Compare Text 字串比較、Microsoft.VisualBasic 執行期函式（Mid/Len/Format/CInt）。決策點：是否允許新程式碼繼續參照 Microsoft.VisualBasic.dll（快但髒）——建議只允許 Phase 1 過渡使用，並以 analyzer 統計殘留量。
  • 先做 Pilot 校準，再量產。選 1 個門診小子系統（例如轉介櫃檯或科室作業，程式數 30–60 支）走完全流程：轉換 → 修整 → 套用 T02/T03/T04 框架 → 對照測試。用它量出「每支程式的實際人日」與轉換器成功率，再重估整體。這是前 6 週最重要的事。
  • 模組順序：醫療共用（8）→ 門診（27）→ 住院（25）→ 急診（7）。共用先做是因為 IC 卡、認證授權、共用系統是所有人的依賴；門診量最大、程式相似度高（掛號／批價／醫囑）最適合量產；急診放最後，因為急診醫囑／藥局大量重用門診與住院已轉好的元件，且急診 24 小時運作，最不適合當白老鼠。
  • 內部 strangler、對外一次上線。開發期間用混語言 solution 逐子系統替換，隨時可以組出「部分 C#、部分 VB」的可跑版本做回歸測試；但規格 貳-一-(一)-5 要求整合測試完成後才在斗六／成大上線，所以對使用者是一次切換（T06）。切換前必須有平行驗證（同一輸入，新舊系統輸出比對），特別是批價、健保申報、藥局的金額與數量。
  • 與總院同步（T05）：轉換期間總院 VB 程式持續改。策略是「凍結點 + 差異重轉」：每支程式記錄轉換時的 VB 版本（commit hash），T05 定期 diff 總院新版，改動小的直接在 C# 端手改、改動大的重跑轉換器。因此版本庫歷史是 P0 資料，沒有它就無法知道哪些程式在我們轉換之後又被改了。

工作量怎麼估的

基準數量 3,647 + 262 = 3,909 支（本機獨立程式未計）。依複雜度分三級，假設工具轉換成功後的人工修整＋套框架＋單元／對照測試的人日：

  • A 級 簡單查詢／維護／報表畫面，約 50%：0.5 人日／支
  • B 級 一般作業畫面（掛號、櫃台、護理站書記等），約 35%：1.5 人日／支
  • C 級 核心複雜（門診／住院／急診醫囑、批價、健保申報、IC 卡、藥局、手術麻醉），約 15%：6 人日／支

加權平均 = 0.5×0.5 + 0.35×1.5 + 0.15×6 ≈ 1.68 人日／支 → 3,909 × 1.68 ≈ 6,560 人日 ÷ 21 ≈ 312 人月，取 300 人月。這不含 T02／T03／T04 的框架設計本身（另計）、T05 的同步合併、T06 上線。區間：若程式碼乾淨、轉換器成功率高、院方有既有測試案例 → 約 180 人月；若必須大量手寫（例如程式嚴重依賴 late binding 與泛用 SQL 介面，轉換器產出不可用）→ 600 人月以上。

時程含意：Phase 1 為 300 天（約 10 個月），扣掉整合測試與兩院上線至少 2 個月，開發窗口約 7–8 個月 → 需要 35–45 位開發＋測試人力同時投入。這是投標前就要面對的人力問題，不是專案管理可以解決的問題。

會讓估算大幅移動的因素：(1) 實際程式行數與每支平均大小（我們現在只有「支數」）；(2) 內嵌 SQL 的比例與是否有泛用 ExecuteSql 介面；(3) 是否有任何自動化測試或測試案例；(4) 本機獨立程式盤點結果；(5) .NET 版本決策；(6) 院方能配合的驗收測試人力。

需要的領域知識與難點

  • 健保業務規則：門急診健保、住院健保、事前審查、重大傷病、P4P/TCPI、健保試辦計畫這些子系統的邏輯是法規邏輯，「功能一致」意味著申報檔格式與金額計算一個位元都不能差。我們需要懂健保申報格式（門診／住院醫療費用點數申報）的人在測試設計中。
  • IC 卡（健保卡）作業：醫療共用的 IC 卡子系統依賴健保署讀卡機控制軟體 SDK（cshis.dll 這類），VB 的 P/Invoke 宣告轉 C# 時 marshalling 極易出錯；且測試要有測試卡與 SAM 卡環境。
  • 醫囑與藥局流程：醫囑檢核（劑量、交互作用、過敏）、給藥確認、配奶室奶囑、化療（腫瘤中心）等都是病安高風險，轉換後的行為差異可能直接傷害病人。這類程式的對照測試要有臨床藥師或資深護理資訊人員參與。
  • VB.Net 語意陷阱：上面遷移策略列的那一串（Option Strict Off、IIf、整數除法、字串比較、Nothing 對值型別的意義、Err 物件）。這些不是語法問題，是「同樣的程式在 C# 跑出不同結果」的問題，轉換器不會幫你抓。
  • 15 年程式碼的考古：沒有文件的死程式、被複製貼上十次的批價邏輯、只有某位已離職同仁知道為什麼的 hard-code 日期。我們需要院內 HIS 組每個子系統的 owner 名單。

依賴關係

前置任務

  • T02 — 院區差異參數化的設計必須在量產轉換前定案（CampusContext 介面、設定優先序、策略對映方式）。否則轉換好的 3,900 支程式之後要再改一次去接 Context，等於做兩遍。我們設定「T02 設計凍結」為量產轉換的 gate，時間點約第 6–8 週；T02 的實作（把所有差異搬進設定表）則與 T01 平行、逐子系統進行。
  • 非正式前置（設計 gate，不列入 depends_on）：T03 檢核引擎的介面與 T04 資料存取層的介面同樣要在量產前凍結，但它們的完成反過來依賴 T01 的進度，所以我們把它們的關係定為「T03／T04 依賴 T01」，並在 T01 內設計 gate。

依賴本任務的任務

  • T03、T04 — 逐支程式套用檢核引擎／搬 SQL 的工作，是隨 T01 轉換每支程式時一起做的。
  • T05 — 同步總院增修的前提是每支程式有「轉換基準版本」。
  • T06 — 斗六／成大上線的東西就是 T01 的產出。
  • T07～T14、T16 — 老醫功能都是在 C# 版上開發的。
  • M02 — 技術移轉的對象是新程式碼與新架構文件。

主要阻礙與風險

  • 量 × 時程 × 人力不成立 — 3,900 支在 7–8 個月開發窗口內轉完，需要 35–45 人同時投入且轉換器成功率要高。人力若只有 15–20 人，Phase 1 必然逾期，而 Phase 1 是 50% 付款。投標前要做 Pilot（哪怕只用抽樣程式碼）驗證每支人日。
  • 原始碼不完整或不能建置 — 15 年系統常見：某些 DLL 沒有原始碼、某些程式線上版本與版本庫不一致。任何一種都會讓「功能一致」變成無法驗證。
  • 「功能一致」沒有客觀判準 — 沒有測試案例、沒有規格文件時，驗收會變成使用者主觀比對。必須在 M01 工作計畫書內定義驗收方式（對照測試清單 + 平行運行期間的差異率門檻）。
  • 移動的目標（T05） — 轉換期間總院持續改版，健保署規則改就得改。若無版本紀律（每支程式的基準 hash）與定期合併節奏，最後會有「不知道哪一版才對」的混亂。
  • VB 語意差異造成靜默錯誤 — 尤其批價金額、日期處理、字串比較。這種錯誤不會當機，會在申報時被健保署核刪才發現。對策：C 級程式強制做新舊系統輸出比對，而非只做功能測試。
  • T02／T03／T04 設計太晚凍結 — 轉好的程式要回頭改。對策：前 8 週集中做框架與 Pilot，量產前必須 gate。
  • 院方配合測試人力 — 貳-三-5 要求與院方使用者及資訊人員共同測試；67 個子系統要各單位派人，院方能否排出這麼多人是我們控制不了的。
