T16

老人醫院上線，再以含老醫功能之版本回饋成大醫院、斗六分院上線

專案的終點：老人醫院開院當天用新 HIS 開門，之後把「含老醫功能的版本」推回成醫與斗六，讓三院跑同一套碼——這是最後 20% 付款與整案驗收的條件。難點不在技術而在時間與控制權：Phase 2 到第 540 天，Phase 3 到第 630 天，只有 90 天要做三次上線，而老醫的開院日期與硬體由院方決定。我們需要一個發布列車 + 分支模型，讓老醫版本回到另兩院時不帶回歸，也需要一個當開院延期時的解耦方案。

規格原文依據

貳-一-(五)：「上線順序配合老人醫院硬體設備及開院時程，與院方討論後訂定。…2. 老人醫院上線。3. 將此版（含老人醫院功能）回饋於成大醫院上線。4. 將此版（含老人醫院功能）回饋於斗六分院上線。」

壹-四-6：「協助老人醫院系統上線，以及成大醫院、斗六分院系統的更換，使三院同步為一套 HIS。」

貳-三-4：「HIS 服務不能中斷，需求調整亦需持續上版，得標廠商必須提供規劃以確保新舊版本功能一致。」

三階段表：第三階段「老人醫院系統建置與上線；以老醫版本於斗六、成醫上線」，交付「教育訓練簽到表與教材、原始程式碼（電子檔）」，決標次日起 630 天內，付款 20%。

規格未載明老醫開院日期，也沒說開院延期時 630 天的履約期限如何處理。「與院方討論後訂定」是我們唯一的槓桿：要在工作計畫書裡寫進「老醫開院晚於第 X 天時，成醫／斗六先行升級至含老醫功能之版本（老醫功能以院區參數停用）」的解耦條款。

我們預期的系統樣貌

從第 300 天起就要以這個分支模型運作，不是到 Phase 3 才開始。核心原則：一份碼、一個 build、三套院區參數——老醫功能不是另一個分支，而是同一個 build 裡由 T02 參數啟用的功能。

元件與資料流

  • 發布列車：main 每 4 週一班（release/1.x），只載總院增修（T05 時期 B）與 hotfix，服務成醫／斗六正式環境。develop 每 2 週從 main merge 一次，老醫功能與介接（T09–T14、H01–H09）以 feature 分支進 develop，經 SIT 才能合併。任何進 develop 的 DB 變更必須是 expand-only（新增表／欄位、新 stored procedure 版本），舊 build 仍能跑——這是 v2.0 回饋兩院時能回退到 v1.x 的前提。
  • 回歸防線：(1) T01／T05 的自動化測試在兩條分支上都跑；(2) 每次 main→develop merge 後跑成醫院區參數的完整回歸（不是只跑老醫）；(3) v2.0-rc 在成醫 UAT 環境以成醫參數跑一輪端到端（掛號→批價→藥局→住院），證明「老醫功能關閉時成醫行為不變」；(4) 跨院功能雙向測試：成醫查老醫床位、老醫查成醫排程都要在 rc 上做，因為 T09–T14 的另一端就是成醫。
  • 老醫上線：新醫院沒有舊系統，「cutover」其實是「開院日」——沒有回退對象，只有「降級運作」（例如中台故障時跨院查詢停用、單院作業繼續）。開院前一週做 dress rehearsal：真實動線走一遍（掛號→檢傷→診間叫號→開立→藥包機→繳費機→慢箋機），H01–H09 每台設備都要在 rehearsal 裡有成功紀錄。開院後 hypercare 3 週，現場 3 人。
  • 回饋成醫：C#→C# 升級，比 Phase-1 簡單得多——同一顆 DB、同一套 client launcher、無 VB 並存。仍沿用 T06 的波次（門診→急診→住院）但可壓縮到 2 週；回退 = launcher 指回 v1.x build，DB 因 expand-only 不需回滾。成醫升級後跨院功能才是雙向的（成醫使用者可查／訂老醫資源），這也是為什麼順序不能反過來太久。
  • 回饋斗六：與成醫共用 DB 與碼（若 T06 確認為真），成醫升級後斗六只是 client 切換與院區參數驗證，1 週。
  • 驗收交付：三院同一 tag 的原始碼（含建置腳本與三套院區參數）、教育訓練簽到表與教材（M02 + T15 使用者訓練）、以及 T05 變更登錄簿作為「新舊版本功能一致」的證據。保固（M04）從此起算。

工作量怎麼估的

發布工程：分支模型、CI、雙分支自動化回歸、expand-only 檢查（4 人月）。老醫開院：rehearsal、開院日與 3 週 hypercare、設備現場（6 人月）。成醫回饋：rc 回歸、波次切換、2 週 hypercare（8 人月）。斗六回饋（3 人月）。驗收文件、原始碼整理、最終交付（3 人月）。開院延期的待命與解耦方案執行緩衝（4 人月）。合計 28 人月。這個數字假設老醫開院在第 540–560 天之間；若開院在 600 天後，本任務無法在 630 天內完成，人力估算失去意義，要改談履約期限。

需要的領域知識與難點

  • 新醫院開院的作業現實：開院第一天通常只開部分門診，住院逐週開床；HIS 要支援「部分科別開放」的參數，且第一個月主檔異動頻繁（新增醫師、新增診間），T15 的差異補轉機制要能持續用。
  • 跨院功能的雙端一致性：T09–T14 每個功能在成醫端與老醫端行為要對稱，但兩院院區參數不同（例如老醫沒有急診就沒有急診床）；回歸測試要以「院區 × 功能」為矩陣。
  • 成醫升級的變更疲勞：成醫使用者在第 300 天剛換過一次系統，第 580 天再升級一次，接受度與訓練負擔要與護理部、醫務部溝通；這次升級對他們的可見變化應盡量小。
  • 健保申報與月結時序：三次上線都要避開每月 1–20 日申報期與月底批次，90 天裡實際可用的切換窗只有 3–4 個。
  • 版本管理與資安要求：伍-三-6 要求版本管理與存取紀錄，伍-三-8 要求正式環境清除測試帳號；每次上線都要重做一次檢核。

依賴關係

前置任務

  • T15 — 環境、基本資料、連線、權限、client 全部就緒是開院的硬前提。
  • T06 — 成醫與斗六必須已在 C# v1.x 上，v2.0 才能「回饋」；並存 launcher 與波次機制直接重用。
  • T05 — 時期 B 的 main→develop 合併確保 v2.0 含所有總院增修；沒做到，回饋等於功能倒退。
  • T09–T14 — 老醫特定功能是 v2.0 的內容；未完成的功能只能以參數關閉、列入驗收保留項。
  • H01–H09 — 開院日每台設備要能用；任一介接未完成，該作業流程要有人工替代方案。
  • X01 — 26 個院內系統介接測試完成是老醫 UAT 結案條件。
  • 間接：T08 中台是跨院功能的資料來源；M03 三次上線前各需資安檢核；M02 技術移轉需在驗收前完成。

依賴本任務的任務

  • M04 — 保固一年自驗收起算；三院版本一致才有可維護性。
  • 整案驗收與 20% 付款。

主要阻礙與風險

  • 開院日期在院方手上、履約期限在我們頭上 — 這是全案最不對稱的風險。老醫硬體採購、建照、評鑑任何一項延誤都直接吃掉 90 天窗口。
  • Phase 2 與 Phase 3 幾乎沒有緩衝 — 540 天 Phase 2 驗收與 555 天開院之間只有兩週，Phase 2 若延遲，老醫只能帶著未驗收的功能開院。
  • 回饋帶入回歸 — 沒有雙分支回歸與 expand-only 紀律，v2.0 在成醫會打壞已穩定的 v1.x 行為；成醫是三院中量最大的，回歸的代價最高。
  • 三次上線擠在 3–4 個切換窗 — 健保申報期讓可用時段極少，任一次延誤會連鎖推到 630 天以後。
  • 設備介接的長尾 — H01–H09 有原廠黑盒子，任一台在 rehearsal 才發現問題，開院日就要人工替代。
  • 院方在時期 B 的開發紀律 — 若院方直接改正式環境或跳過 release 分支，分支模型形同虛設。
