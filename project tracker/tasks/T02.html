T02

院區差異參數化

把成大、斗六、老人醫院三院之間的行為差異，從散落在 3,900 支程式裡的 if-else 抽出來，變成「一套程式碼 + 每院一組設定」。這是專案目標「各院區程式邏輯以設定方式完成」（壹-四-2）的落實，也是「作為後續新建醫院快速建置基礎」的關鍵：第四家醫院應該是加一列設定，不是再改一次程式。T02 的設計必須在 T01 量產轉換前定案，否則轉換要做兩遍。

規格原文依據

貳-一-(一)-2：「各院區差異性以參數化方式撰寫，讓程式簡潔、易於修改與維護：沿用與擴充 APP Config、WEB Config 等設定檔；載入院區全域變數，Context 類別（例如 user name、account、pwd、department、station、IP 等）；將 if … else … 段落改寫簡化，例如以字典取代或使用函式映射；將共用性高但各自撰寫的段落整理出來進行參數化設計；擴充資料庫表格相關設定，如 PCS_Ip_Config、PUB_Config 等；新增資料庫表格進行設定與維護。」

壹-四-2：「各院區程式邏輯以設定方式完成。」壹-四-6：「……使三院同步為一套 HIS。」貳-一-(一) 前言：「保留擴充彈性，可作為後續新建醫院快速建置與導入之基礎，易於集中開發與管理。」

規格給了機制的清單（Config 檔、Context 類別、字典／函式映射、設定表），但沒有列出任何一項實際的院區差異——斗六與成大目前差在哪裡、老人醫院會差在哪裡，規格未載明，需確認。這代表 T02 有一半是考古工作。

我們預期的系統樣貌

核心概念：程式只認識一個 CampusContext，所有院區相關的值與行為都從它拿；它由三層來源合成（DB 設定表 > 設定檔 > 程式預設），且院區「行為」差異走策略對映，「數值」差異走設定表。任何 Form 或 Service 內出現 if (campus == "DL") 就是缺陷，用 Roslyn analyzer 擋在 build 階段。

元件與資料流

  • CampusContext：登入時解析一次、session 期間不變的物件；WinForms 端放在 DI 容器的 scoped 實例，WCF 端從 message header（CampusId + 站台）重建，不信任 client 傳來的整包 context。規格列的 user name／account／pwd／department／station／IP 都在裡面；pwd 不應存在 Context 內（資安，見 T04／M03），改存 token，需跟院方溝通。
  • 設定優先序（DB > 檔案 > 預設）：DB 表可由院方資訊人員在不重新部署下改；設定檔管環境相依（連線字串、服務 URL、憑證）；預設值讓新院區「未設定即等同總院」，避免新院區要填幾百個值才能開機。每個設定 key 有 scope：Global / Campus / Station，同 key 取最細者，寫進 CAMPUS_SETTING 新表（規格說「新增資料庫表格進行設定與維護」）。
  • 行為差異 = 策略介面 + 註冊表：每一類差異定義一個小介面（如 IRegistrationFeePolicy、IDischargeFlowPolicy），預設實作是「總院行為」，只有真的不同的院區才註冊 override。註冊表是 Dictionary<(PolicyType, CampusId), Implementation>，找不到就退回 Default。這就是規格的「字典取代／函式映射」，同時避免每個策略都要為三院各寫一份。
  • 如何避免 switch(campus) 爆炸：(1) 規則——院區判斷只允許存在於 HIS.Campus.* 組件內，其他組件出現 CampusId 比較即 build error（自寫 Roslyn analyzer）；(2) 差異只能以「override 預設」表達，不能以列舉所有院區表達；(3) 用功能開關（FeatureFlags）處理「某院有／沒有這功能」，用設定值處理「數值不同」，用策略處理「流程不同」——三種各有明確去處，不混用；(4) 設定表有 UI 可維護與稽核紀錄（誰改了什麼），否則上線後會回到改程式。
  • PCS_Ip_Config／PUB_Config 擴充：現行表格推測以 IP 或站台對應設定；擴充方式是加 CampusId 欄與 Scope，並提供 view 讓舊程式在過渡期繼續讀舊欄位。表結構規格未載明，需取得 DDL 與現有資料。
  • 三院差異怎麼被找出來（規格裡沒有，只能挖）：
    1. 對 VB 原始碼做靜態掃描：找機構代號、院區名稱、斗六 IP 網段、Station Like "DL%"、設定檔 key 等模式，產出「疑似院區分支」清單（預估數百處）。
    2. 比對成大與斗六兩院的 PCS_Ip_Config／PUB_Config／代碼表資料差異（如果兩院各自一個 DB，diff 就是差異清單的一半）。
    3. 與 HIS 組逐子系統訪談確認每處分支的業務理由，分類為「數值／開關／流程」。
    4. 老人醫院差異來自 T07 訪談；T02 只負責機制與老醫「已知會不同」的骨架（無急診？病房型態？長照給付？），內容留給 T07。

工作量怎麼估的

框架（Context、Resolver、設定表 + 維護 UI、策略註冊、analyzer、文件）約 6 人月；差異盤點（掃描工具 + 兩院資料 diff + 67 個子系統訪談）約 8 人月；逐支程式套用（把疑似分支改成策略／設定，估 400–800 處，每處 0.3–0.5 人日含測試）約 16 人月。合計約 30 人月。逐程式套用的部分與 T01 轉換同一支程式時一起做，實務上會被算在 T01 的每支人日內，這裡分開列是為了追蹤。若兩院其實是兩套分岔已久的程式碼（不是一套程式 + 設定），盤點工作量會加倍，且要先決定以哪一版為基準。

需要的領域知識與難點

  • 院區在健保與行政上的身分：每院有自己的健保機構代號、申報身分、特約層級（醫學中心 vs 地區醫院 → 部分負擔、掛號費、病房費差額不同）。這些不是技術設定，是法規；老人醫院的特約層級與是否為總院的分院，會決定申報是分開還是合併，直接影響 Context 的設計（一個病人在兩院的病歷號是否相同？）。
  • 分院實際運作差異：斗六分院規模小，可能沒有某些科室、藥品品項、手術房數；流程上（如出院結帳、藥局窗口數）也不同。這些差異多半藏在程式裡而非文件裡。
  • 老人醫院型態：規格只說「依不同作業流程客製化」。老人醫院是否有急診？是否有長照／復健／安寧？門診量級？這些會決定哪些 FeatureFlag 要先設計。
  • 技術難點：Context 在 WinForms、WCF、批次三種宿主的生命週期不同（批次沒有登入者、可能一次跑多院）；WCF 端要把 CampusId 當成安全邊界（斗六站台不得存取成大資料，除非是 T09～T14 明定的跨院查詢）。
  • 設定值的正確性責任：一旦邏輯變設定，設定錯就是功能錯。要有設定的版本管理、比對工具（三院設定 diff）與變更稽核，這部分規格沒要求但沒有它會出事。

依賴關係

前置任務

  • 無正式前置任務。但需要 T01 的 P0 資料（原始碼、DB DDL、兩院設定表資料）才能開始盤點；設計本身可在拿到原始碼後 4–6 週內定案。

依賴本任務的任務

  • T01 — Context 介面、設定優先序、策略註冊方式定案後，量產轉換才能把院區分支直接改成正確形式，不必二次返工。這是 T01 的 gate。
  • T07 — 老人醫院差異訪談的產出要能落到 T02 的三種容器（設定／開關／策略）裡；T02 提供「差異登錄表」格式給訪談用。
  • T15 — 老醫上線環境準備中的「基本資料轉置」與連線設定，就是填老醫那一欄的設定值。
  • T16 — 三院同一版本上線的前提是三院差異全在設定內。

硬體／外部設備介接

無直接硬體介接。但站台層級的設定（哪台電腦接哪台印表機、讀卡機 COM port、叫號機對應診間）是 Context 的 Station scope 要承載的內容，設計時要保留位置給 H01～H09 使用。

需要緊急向院方／原廠取得

優先要什麼向誰要為什麼／沒有會怎樣
P0完整原始碼（同 T01 P0）＋ PCS_Ip_Config、PUB_Config 及所有設定／代碼表的 DDL 與成大、斗六兩院的實際資料；app.config／web.config 兩院版本資訊室 HIS 組院區差異不在規格裡、只在程式與資料裡。沒有這些，T02 只能設計空框架，T01 量產時仍不知道哪些 if-else 是院區分支。
P0回答：斗六與成大目前是「同一套程式 + 設定切換」還是「兩份分岔的程式碼」？同一 DB 還是分開？病歷號是否共用？資訊室 HIS 組決定 T02 是「抽取」還是「合併」，工作量差一倍；也決定 Context 是否要處理跨院病人主索引。
P1現行已知的院區差異清單（哪怕是口頭／Excel），與斗六分院資訊承辦聯絡人資訊室 HIS 組、斗六分院資訊人員訪談起點；沒有就純靠程式掃描，會漏掉靠人工流程繞過的差異。
P1老人醫院基本身分資訊：健保機構代號／特約層級是否已定、是總院分院還是獨立院所、預計科別與有無急診、開院時程老人醫院籌備處、醫事室／健保業務單位決定申報身分模型與第一批 FeatureFlag；未定就以「與斗六同型」假設設計，之後可能重做。
P1院方對設定維護的責任分工：上線後誰有權改 CAMPUS_SETTING？需不需要審核流程？資訊室 HIS 組決定要不要做維護 UI 與稽核（我們建議要），影響 2–3 人月。
P2院方對 Context 內含「pwd」的意圖說明，以及帳號／權限來源（AD？認證授權子系統？）資訊室 HIS 組、資安承辦規格字面把密碼放進 Context，與 M03 資安要求衝突；需在設計審查時一起定案。

主要阻礙與風險

  • 差異未知且不在文件裡 — 最大風險。盤點漏掉的分支會在斗六上線時以「功能不對」的形式出現。對策：掃描工具 + 兩院資料 diff + 斗六試營運期間的差異回報機制。
  • 兩院程式碼已分岔 — 如果斗六跑的是一份改過的副本，「一套程式」得先合併再參數化，且要決定誰是基準（通常是總院），斗六的獨有修改要逐一評估。
  • 設計定案太晚拖住 T01 — T02 設計是 T01 量產的 gate；若原始碼晚到或院方決策慢，整個轉換排程往後推。對策：設計以「可擴充的最小版本」在第 6 週前凍結，之後只加不改。
  • 過度設計 — 把每個差異都做成策略介面，會產生上百個小介面沒人維護。原則：數值走設定、開關走 flag，只有流程真的分岔才做策略；每個策略要有真實的第二種實作才存在。
  • 設定錯誤取代程式錯誤 — 沒有設定 diff 工具、沒有稽核，上線後改錯一個值就是全院事故。
  • 老醫差異來得太晚 — T07 訪談在 Phase 2；若 Phase 1 的 Context 沒預留老醫需要的維度（例如病房型態、長照給付），Phase 2 要改框架。

待確認問題

  1. 斗六與成大：同一程式碼？同一 DB？同一病歷號體系？目前用什麼判斷院區（IP 網段、站台代碼、登入帳號）？
  2. PCS_Ip_Config、PUB_Config 的實際結構與用途？還有哪些「設定型」資料表（代碼表、參數表）散在各子系統？
  3. 院方是否接受設定優先序 DB > 設定檔 > 預設？是否有值必須只能在設定檔（例如連線字串）？
  4. 老人醫院是否有急診／手術／ICU？是總院分院（同機構代號體系）還是獨立特約院所？開院時程？
  5. 跨院資料存取的邊界：斗六站台能否查成大病人資料？現況如何？（影響 Context 的安全語意，也影響 T09～T14）
  6. 院方是否要求設定維護 UI 與變更稽核？誰是設定的 owner？
  7. 批次程式的院區語意：一支批次跑三院，還是每院各排一次？
  8. Context 內的「pwd」是否可以改為 token／session id？認證來源是什麼？
  9. 驗收 T02 的判準：analyzer 零違規？差異登錄表 100% 對應到設定？誰簽核？
