T09

跨院掛號資料查詢與辦理掛號（老人醫院 ↔ 成大）

讓老人醫院的櫃台／醫師能查到病人在成大醫院的掛號與預約紀錄，並直接替病人掛成大的診（反向亦然）。查詢走 T08 中台的讀取副本；「辦理掛號」是寫入動作，必須以跨院命令打回擁有該診次的院區核心 HIS，由該院的掛號規則引擎放號。這是 Phase 2 六個跨院共享功能裡最貼近病人、最常被用、也最容易踩健保與院內規則地雷的一個。

規格原文依據

貳-一-(二)「老人醫院醫療資訊系統功能」第 1 點：「查詢老人醫院及成大醫院掛號資料，並辦理掛號。」

貳-一-(二)-7 數據整合中台：「配合跨院區作業查詢需求，透過資料即時供應機制（例如 CDC、MQ 或 Replication）提升資料即時性與效能，保護核心 HIS 資料庫並達到讀寫分離……跨院資源共享：掛號資訊、床位資訊、檢查科室儀器排程、開刀房手術排程、檢驗抽血、營養供膳等。」

貳-一-(二)-8：「以上老人醫院特定需求，於專案會議訂定的需求訪談會議中再進行細部需求收集與確認，作為開發的基準範圍。」

附錄子系統清單（門診 27 個）含「掛號系統」、「門急診健保系統」、「全院排程」、「轉介櫃檯」；醫療共用含「IC 卡」、「病患就醫資訊整合」、「認證授權系統」。

規格只寫了一句話。「掛號資料」的範圍（門診預約？急診？住院預約？健檢？）、「辦理掛號」是否含取消／改期／退掛、是否含現場號，全部未載明，需在 T07 訪談中定案。

我們預期的系統樣貌

兩條路徑分開設計：讀走中台副本（快、可承受大量查詢、不碰核心 DB）；寫走「跨院掛號命令」API，由擁有該診次的院區 HIS 執行其原生掛號邏輯（號序、額滿、特約、健保檢核），中台只是事後透過 CDC 把結果同步回來。絕不能讓老人醫院直接寫成大的掛號表。

元件與資料流

  • 讀路徑（T08）：診次主檔（科別、醫師、診別、時段、可掛總號、預約上限、現場保留）、醫師排班、停診／代診公告、病人既有預約、看診進度。中台需保證延遲在「秒級」，否則畫面顯示有號、送出卻額滿，櫃台會抱怨。
  • 寫路徑（跨院掛號命令）：RegisterCommand{sourceCampus, targetCampus, patientKey, sessionId, slotType(預約/現場), operator, idempotencyKey}。目標院區的掛號服務以原生規則放號並回傳掛號序號、看診號、預估時間；衝突（額滿、重複掛號、停診）回傳結構化拒絕碼，不可只回字串。命令與結果都寫入跨院審計表（誰、何時、從哪院、替誰、掛了哪院哪診）。
  • 取消／改期：同樣以命令進入擁有院區；改期 = 取消 + 掛號兩個命令包成一個 saga，任一步失敗要有補償。
  • 病人身分：跨院查詢要先確認「哪個病人」。若三院共用病歷號（總院系統延伸），問題小；若老人醫院另發病歷號，需要 EMPI 或至少身分證字號＋出生日期比對，並處理外籍／新生兒／無身分證的特例。
  • 院區參數（T02）：診次結構、號序規則、掛號費、特約規則、可掛天數、身心科／特殊門診限制，全部以 T02 的設定機制表達，不能在程式碼裡寫 if campus == "老醫"。
  • 健保：跨院掛號本身不需讀 IC 卡（病人不在現場），但目標院區到診時仍需過卡；預約時要標示「未過卡」狀態。慢箋、轉診單優先、部分負擔等級與掛號時的檢核由目標院區規則負責。

工作量怎麼估的

約 10 人月：讀取畫面與中台查詢 2 人月；掛號命令 API 與目標院區掛號服務封裝（把現有 VB.Net 掛號邏輯抽成可被遠端呼叫的服務，含 idempotency、衝突碼、審計）4 人月；取消／改期 saga 1 人月；病人索引／身分比對 1 人月；院區參數化與測試（含與成大掛號組聯測、健保情境）2 人月。前提是 T01 已把掛號子系統改寫成 C# 且 T08 的 CDC 已把掛號相關表同步到中台；若掛號邏輯仍散在 VB.Net 前端，封裝成本會翻倍。

需要的領域知識與難點

  • 診次／時段／號序模型：每院每科的診次定義（上午／下午／夜診、第幾診）、號碼規則（單雙號、預約號區間、現場號區間、加號、特約號）、看診順序估算。成大與老人醫院極可能不同，且會在專案期間被改。
  • 預約 vs 現場：跨院只能做「預約」，但目標院區可能有「預約號只開放到前一日」「當日只能現場」等規則；需確認跨院掛號能否掛當日。
  • 停診／代診：醫師臨時停診時，已跨院掛號的病人如何通知？由哪個院區通知？代診時是否自動轉號？現有系統怎麼做，跨院要跟上。
  • 特約／限制門診：特約門診、初診限制、身心科、健檢門診、自費門診等常有「只能由某窗口掛」的規則；跨院櫃台不一定有權限。
  • 健保與掛號費：跨院掛號的掛號費、部分負擔由哪院收？病人在老人醫院預約成大的診，是否算轉診？是否有健保「分級醫療」轉診優惠要在掛號時標記？需向兩院掛號組與健保承辦確認。
  • 病人身分：三院是否共用病歷號是本任務最大的未知。若不共用，跨院掛號要先「跨院建檔」或「身分綁定」，這本身是一個小專案。
  • 老人醫院特性：高齡病人常由家屬／照服員代掛、多科同日連掛、輪椅／交通接駁需求、長照機構整批掛號；訪談時要問是否有「跨院多科一次掛」的需求。

依賴關係

前置任務

  • T08 — 讀路徑完全依賴中台的掛號相關表同步（診次、排班、停代診、預約）；中台沒好，本任務只能先做寫路徑的 API stub。
  • T02 — 院區 Context 與參數化：本任務需要「目前院區」「目標院區」兩個 context 同時存在，T02 的 Context 類別設計必須支援這點。
  • T01 — 掛號子系統改寫為 C#，並把掛號邏輯移到後端（配合 T04 SQL 移至後端、WCF HTTPS），跨院命令 API 才有東西可以呼叫。
  • T07 — 訪談定義「掛號資料」與「辦理掛號」範圍、跨院掛號權限、費用歸屬。

依賴本任務的任務

  • T14 轉檢與代檢 — 代檢流程通常會替病人在對方院區掛一個檢查科的診次或排程，會重用本任務的跨院命令與病人身分比對。
  • T12 跨院檢查排程 — 部分檢查在成大需先有門診掛號（醫囑來源），跨院檢查預約會回頭呼叫掛號命令。
  • T16 老人醫院上線 — 本功能是開院日櫃台必用功能。
  • X01 — 跨院介接（部立台南、郭綜合）測試情境可能包含轉診掛號，需要本任務的命令介面。

硬體／外部設備介接

無。跨院掛號是純軟體流程：查詢走中台、寫入走 API。健保 IC 卡讀卡屬「醫療共用／IC 卡」子系統，由病人到診院區的既有流程處理，本任務只需在預約狀態上標示「未過卡」。診間叫號機（H02）只消費目標院區的看診序號，不由本任務直接介接。

主要阻礙與風險

  • 病人主索引未定 — 若三院不共用病歷號且院方無 EMPI，跨院掛號的正確性完全取決於身分比對，錯配即是醫療風險。
  • 掛號邏輯散在 VB.Net 前端 — 15 年的掛號程式多半把放號規則寫在畫面事件裡；若 T01/T04 沒有先把它移到後端服務，本任務無法以 API 重用，會被迫複製一份邏輯（之後兩邊不同步）。
  • 寫路徑的一致性 — 中台副本與目標院區核心 DB 之間有延遲；必須以目標院區的原生程序為唯一真相，並處理重試（idempotency）與競態（同一診次最後一號）。
  • 總院掛號規則持續變動（T05） — 健保署與院內政策每季都會改放號規則；跨院命令的合約要能容納新拒絕碼，而不是每次改一次 API。
  • 權限與稽核 — 跨院操作等於一院員工碰另一院的病人資料，個資與稽核紀錄要求比院內操作高；M03 會來查。
  • 老人醫院診次結構未知 — 開院前科別、醫師、診次都還沒定，測試資料只能先用假設，上線前需要一次完整重測。

待確認問題

  1. 三院是否共用同一病歷號？若否，是否已有或計畫建置 EMPI？規格未載明，需確認。
  2. 「掛號資料」是否包含急診、住院預約、健檢預約？還是僅門診？
  3. 「辦理掛號」是否包含取消、改期、退掛？可否掛當日診？可否加號？
  4. 跨院掛號後，病人到目標院區報到的流程：需要重新過卡、繳掛號費？由哪個系統列印掛號單？
  5. 停診／代診時，跨院掛號病人的通知責任在哪一院？現行簡訊／電話流程是否可沿用？
  6. 斗六分院是否也納入跨院掛號？規格只寫「老人醫院及成大醫院」，但 T16 三院同版本後很可能被要求擴充。
  7. 跨院命令 API 的技術形式：延用 WCF（T04 要求 HTTP/HTTPS）還是院方接受 REST？誰負責兩院間的網路與憑證？
  8. 跨院掛號是否需要與「病患就醫資訊整合」子系統整合，讓醫師在老人醫院看到病人在成大的看診紀錄？
