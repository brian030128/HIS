T05

開發期間與總院增修保持同步

我們改寫的是一個「會動的目標」：在 630 天內，總院 HIS 組仍會依健保署公告與院內單位需求持續改 VB.Net 正式版。若沒有一套固定節奏的變更接收、登錄、移植、回歸機制，Phase-1 上線那天的 C# 版就會比 VB.Net 正式版少掉幾個月的功能，等於上線即倒退。規格只說「必須定期同步」，完全沒給機制，所以這個任務的本質是對院方團隊的流程依賴，要在工作計畫書（20 天內）就把規則訂死。

規格原文依據

壹-四-5：「開發期間須同時定期更新總院持續增修的功能，以達到統一的版本。」

貳-一-(四)：「本案開發期程長，期間總院 HIS 仍須持續配合健保署及院內各使用單位需求進行增修，因此必須定期將線上新增調整的功能同步到本系統，確保程式及功能一致。」

貳-三-4：「HIS 服務不能中斷，需求調整亦需持續上版，得標廠商必須提供規劃以確保新舊版本功能一致。」

貳-三-6：「對設備規格、功能、專案時程或施工作業的任何變更，需與資訊室及專案管理人協商取得許可後方可進行。」

注意規格用詞是「定期」「提供規劃」——沒有定義頻率、沒有定義院方提供變更資訊的方式、沒有說變更誰付費。這些空白全部要在工作計畫書裡由我們填上並請院方簽認。

我們預期的系統樣貌

同步分兩個時期，機制不同。時期 A（第 0–300 天）：總院正式版是 VB.Net，我們的 C# 版還沒上線，變更方向是 VB.Net → C#，靠人工移植。時期 B（第 300–630 天）：成醫與斗六已切到 C#，總院的增修必須直接做在 C# 主線上（不論由院方或我們做），我們的老醫功能分支要定期從主線 merge，變更方向變成 Git 分支合併（分支模型見 T16）。

元件與資料流

  • 變更接收（intake）：三個來源缺一不可。① 院方每次上版的「上版單／變更單」（他們一定有某種上版流程，格式未確認）；② 我們直接對院方 VB.Net 版本庫做 diff（需唯讀帳號）；③ DB 端異動——DDL、PUB_Config／PCS_Ip_Config 之類設定表、檢核規則表。第三種最危險，因為 C# 與 VB.Net 共用同一顆 DB，院方改欄位當天我們的測試環境就可能壞掉，卻不會出現在任何程式碼 diff 裡。
  • 變更登錄簿（Change Register）：一張表，每筆一個院方變更：院方單號、上版日、子系統、VB 程式名、DB 物件、原因分類（健保署／使用單位／bug／資安）、影響院區（成醫／斗六／未來老醫）、對應 C# 模組、狀態（待分析／移植中／已合併／已回歸／延後）、負責人、驗證方式。這張表就是日後「新舊版本功能一致」（貳-三-4）的證據，驗收時會被要。
  • 節奏：雙週同步批次。週一拉 diff 與上版單 → 週二 triage 會議（我們 + 院方 HIS 組窗口，30 分鐘）→ 週三至隔週三移植與回歸 → 隔週四併入 develop。健保署月初／季初的大改版（例如支付標準、申報格式）另開專案性批次。
  • 移植規則：不是逐行翻譯。若該 VB 模組在 T01 已改寫完成，則依 C# 新架構（參數化、SQL 在後端、字典取代 if-else）重做該變更；若尚未改寫，只把變更記入登錄簿並把該模組的「基準快照版本」往前推，等 T01 輪到時一次改。這樣避免同一個模組改兩次。
  • 回歸測試：兩層。第一層是 T01 建立的自動化測試；第二層是「golden output 比對」——對 262 支批次程式與批價／申報類線上程式，用同一份測試資料分別跑 VB 版與 C# 版，比對輸出（申報 XML、批價明細、報表）。這是證明「功能一致」最便宜也最有說服力的方法。
  • 凍結窗：每次上線前 30 天進入凍結，院方只允許健保強制項目與緊急修正，且必須「雙版同時上」（院方改 VB、我們同步改 C#，同一天驗證）。凍結規則要寫進「上線前檢核清單」（M01）。

工作量怎麼估的

總院 HIS 每月變更量規格未載明，需確認。以一套 3,900 支程式、服務兩院區、每月配合健保署與使用單位的中大型 HIS 推估，合理範圍是每月 30–80 筆程式異動加上數筆 DDL。假設平均 50 筆／月、每筆移植加回歸平均 0.5 人日，即每月約 25 人日，再加 triage、登錄簿維護、golden output 環境維護與與院方溝通，需要常駐 2 人；時期 A 約 10 個月、時期 B 約 11 個月（合併衝突比移植便宜但老醫功能會擴大衝突面），取 18 個月 × 2 人 = 36 人月。若院方變更量是每月 150 筆以上，這個數字要翻倍，而且 T01 的估算也會跟著錯，所以「近 12 個月上版紀錄」是 P0 的資料。

需要的領域知識與難點

  • 健保署公告的節奏與衝擊面：支付標準、藥價基準、申報格式（XML 格式版本）、IC 卡 API 版本、慢箋規則等，多數有法定生效日，不能延後。同步小組要有人看得懂健保公告並判斷影響哪些子系統（門急診健保系統、住院健保、藥局、批價）。
  • 看得懂 15 年 VB.Net 舊碼的意圖：院方上版單通常只寫「配合 XX 科需求調整」，真正的邏輯要從 diff 裡讀出來。院方的 commit 粒度與註解品質未確認，若他們是整包覆蓋而非逐檔 commit，diff 會很難讀。
  • 共用 DB 的 schema 演進：VB 與 C# 在時期 A 共用同一顆 DB（否則無法 golden output 比對，也無法 Phase-1 上線）。院方新增欄位、改型別、改 stored procedure，都要在我們的 C# 資料存取層即時反映。
  • 院方團隊的工作方式：這是流程依賴，不是技術問題。若院方 HIS 組沒有指定窗口、沒有固定上版日、變更不留紀錄，我們的節奏就建不起來。
  • 時期 B 的「誰在改 C#」問題：Phase-1 上線後總院增修必須做在 C# 上。若院方要自己改，M02 技術移轉得提前到第 300 天前完成，而且 code review 權要留在我們這邊直到 630 天驗收；若全由我們改，這部分是不是計價範圍要在合約釐清（規格沒寫）。

依賴關係

前置任務

  • T01 — 同步是把院方變更移植到 T01 改寫後的模組上；T01 的改寫順序與「基準快照」版本決定每筆變更是立即移植還是延後。T01 的自動化測試也是本任務回歸測試的第一層。
  • M01 — 同步流程、變更登錄簿格式、凍結規則都必須寫進工作計畫書（得標 20 天內）並納入變更管理程序，否則對院方沒有約束力。

依賴本任務的任務

  • T06 — Phase-1 上線的前提是 C# 版功能追平 VB.Net 正式版；凍結窗與登錄簿「全數已回歸」是上線前檢核清單的一項。

主要阻礙與風險

  • 流程依賴院方團隊 — 規格未給任何機制，成敗取決於院方 HIS 組是否願意配合固定節奏、留紀錄、指派窗口。這不是我們能單方面解決的，要在工作計畫書簽認階段就談定。
  • 變更量未知 — 每月 30 筆與 150 筆是完全不同的專案；後者會吃掉 T01 的人力並讓 300 天上線不可能。
  • 共用 DB 的隱形變更 — DDL 與設定表異動不在程式 diff 中，是最常造成「測試環境突然壞掉」的來源。
  • 健保署強制時程壓過凍結窗 — 健保改版有法定生效日，凍結窗擋不住；只能靠 dual-ship 與縮小影響範圍。
  • 院方 commit 品質 — 若院方版本庫是整包覆蓋、無註解，diff 的可讀性極低，移植成本會加倍。
  • 時期 B 雙軌開發衝突 — 300 天後總院增修與老醫功能同時在 C# 上進行，若沒有嚴格分支模型與 code owner 制度，回饋版本會帶入回歸。
